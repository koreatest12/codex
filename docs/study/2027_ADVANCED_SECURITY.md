# 2027–2029 정보보안기사 신규·심화 개념: 정의 → 위협 → 통제 → 검증

> **자체 작성 학습노트 | 공식 기출·공식 정답 아님.** 공식 출제기준(사용자 제공 PDF) 필기 1–5쪽 / 실기 6–11쪽을 [대응표](./2027_EXAM_CROSSWALK.md)로 연결한다. 명령은 **소유·허가된 실습 시스템**에서만 사용한다. 도구 결과는 취약점 또는 침해의 최종 확증이 아니다.

## 1. 클라우드·가상화·컨테이너 보안 (필기 시스템 1–2쪽, 실기 6쪽)

- **IaaS**: 가상 인스턴스·가상 네트워크·스토리지의 운영 및 게스트 OS 보안이 사용자 책임인 경우가 많다. **PaaS**: 런타임 관리 일부를 제공자가 맡고 코드·데이터·구성·접근은 사용자가 관리한다. **SaaS**: 애플리케이션 운영 대부분을 제공자가 수행하더라도 사용자 데이터 분류·계정·권한·설정·접속 정책은 여전히 중요하다. 책임 범위는 공급자 계약과 상품별로 확인한다.
- **VM vs 컨테이너**: VM은 게스트 OS를 포함하고 하이퍼바이저를 경유한다. 일반적인 컨테이너는 호스트 커널을 공유하므로 커널 취약점, 특권 컨테이너, 마운트, 네임스페이스·capabilities 설정에 특히 주의한다. '컨테이너 = 완전한 보안 경계'는 오해다.
- **대표 위험**: 외부 공개 관리 포트, 과도한 IAM 권한, 잘못된 스토리지 공개, 이미지의 알려진 취약점·하드코딩된 비밀, 불필요한 root 실행, 관리 인터페이스 노출, 감사 로그 누락.
- **방어**: 최소권한 RBAC/IAM, IaC 구성 점검, 이미지·의존성 스캔, 서명·출처 확인, 비밀관리, 주기적 패치·재빌드, 제한된 egress, 로그 보존. 스캔 **발견→재현 가능한 설정 확인→자산 영향→조치→재검증** 순서를 지킨다.
- **클라우드 인스턴스 메타데이터**: 인스턴스 정보·일시 자격증명 등이 제공될 수 있어 SSRF·과도한 권한과 결합하면 위험해진다. 메타데이터 접근 통제와 자격증명 최소화가 핵심이며 공급자 구현별 보호 방법은 다르다.

### Trivy vs ScoutSuite vs Nmap

| 도구 | 주요 대상 | 답할 수 있는 질문 | 할 수 없는 일/주의 |
|---|---|---|---|
| **Trivy** | 컨테이너 이미지·파일시스템·IaC 설정 등 | 알려진 취약점·구성오류·일부 시크릿 노출 지표가 있는가? | 런타임 공격 성공·비즈니스 인가 오류를 단독으로 증명하지 않음 |
| **ScoutSuite** | AWS·Azure·GCP 등 계정의 **클라우드 구성** | 계정·네트워크·스토리지 등 구성의 위험 신호는? | 모든 위험의 실악용 여부·자산 중요도를 자동 확정하지 않음 |
| **Nmap** | 허가된 호스트의 네트워크 서비스 | 어떤 포트·서비스가 응답하는가? | 열려 있음=취약/침해라는 뜻 아님. 타인 대상 무허가 스캔 금지 |

#### 읽기 전용 실습 A: 로컬 IaC 파일 점검

아래 코드는 **만들어 놓은 샘플 Dockerfile**만 평가한다. 빌드·배포하지 않는다.

```bash
mkdir -p /tmp/security-exam-2027
cat > /tmp/security-exam-2027/Dockerfile <<'EOF'
FROM alpine:3.20
USER root
CMD ["sh", "-c", "echo demo"]
EOF
# Trivy를 본인이 설치한 경우에만:
trivy config /tmp/security-exam-2027
```

**관찰 목표:** 경고 유형과 설명을 확인하고, 'root 실행'이 경고되는 경우 권한 축소 방안을 제시한다. **도구 버전·정책집에 따라 탐지/심각도가 달라질 수 있으며 결과를 미리 단정하지 않는다.** 버전 태그도 예시일 뿐 운영 이미지 최신성 보장이 아니다. Trivy의 이미지 점검은 별도 `trivy image <소유한-이미지:태그>`로 수행할 수 있다. ([Trivy 공식 사용 안내](https://trivy.dev/docs/latest/scanner/misconfiguration/))

#### 읽기 전용 실습 B: 클라우드 설정 점검 계획

- ScoutSuite는 클라우드 API를 통해 구성 정보를 수집하고 보고서를 만든다. **별도 실습 계정·최소 읽기 권한·동의된 범위**를 먼저 확보한다.
- 실행 전: 계정 ID/역할/읽기 권한 범위, 비용·API 호출 영향, 로그 및 보고서에 포함될 민감정보 확인. 보고서는 **GitHub에 올리지 않는다**.
- 점검표: 관리 포트 공개 여부 → 스토리지 공개 여부 → IAM 과권한 → 로그 설정 → 탐지의 사실 여부를 콘솔 설정과 정책으로 재확인. ([ScoutSuite 공식 프로젝트](https://github.com/nccgroup/ScoutSuite))
- 네트워크 기초 실습은 타인 주소 대신 **본인 PC의 localhost**에서 `nmap -sT -p 8080 127.0.0.1`처럼 제한한다(설치 시). 포트가 닫힌 이유는 서비스 미실행, 방화벽, 바인딩 등 여러 가능성이 있다.

## 2. VPC / Security Group / NACL (실기 7쪽)

- **VPC**: 클라우드에서 논리적으로 격리한 IP 주소·서브넷·라우팅 등의 네트워크 환경. **서브넷**은 주소 범위를 분리하며 '퍼블릭/프라이빗' 여부는 라우트·공인 IP·게이트웨이 등 구성을 함께 봐야 한다.
- **Security Group (AWS 예)**: 인스턴스 네트워크 인터페이스 등 리소스에 적용하는 **상태 저장(stateful) 허용 규칙**. 허용된 연결의 응답 흐름은 자동 허용될 수 있다. **NACL**은 서브넷 수준의 상태 비저장(stateless) 허용/거부 규칙이다. 공급자/서비스별 세부 동작은 다르다.
- **예:** 웹 서버 SG 인바운드 TCP/443은 필요한 출발지에서만 허용, 관리 TCP/22는 고정된 관리자 IP 범위만 허용, DB 서버 TCP/5432는 애플리케이션 SG에서만 허용. '0.0.0.0/0:22'와 '누구나 DB 접근'은 일반적인 노출 위험이다.
- **구분:** 라우팅에 경로가 있다고 해서 SG가 허용하는 것은 아니며, SG만 구성해도 애플리케이션의 ID/객체별 인가는 보장되지 않는다. Security Group은 **허용 규칙**이며 고급 차단 정책이 필요하면 추가 계층을 고려한다.

**검증 질문:** 인터넷 사용자 A가 DB에 연결 가능한지 판단할 때 'DB SG 인바운드 규칙'만 보지 말고 **네트워크 경로, 공인 엔드포인트, NACL, SG, 서비스 인증**을 함께 확인할 것. ([AWS 공식 VPC](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html))

## 3. SASE · ZTNA · XDR · EDR · SIEM (필기 네트워크 3쪽, 실기 EDR/EPP 7쪽)

| 기술 | 핵심 목적 | 대표 구성·주의 |
|---|---|---|
| **SASE** (Secure Access Service Edge) | 네트워크 연결 기능과 클라우드 전달 보안 기능을 결합 | SD-WAN + SWG/CASB/ZTNA/FWaaS 등은 제품별 편차 있음. '단일 필수 제품 구성' 아님 |
| **ZTNA** (Zero Trust Network Access) | 사용자·기기·상황·자원 단위 접근 판단 | 신원·기기 상태·정책에 따른 최소권한, 지속적 재평가. 단순 VPN 교체와 동일 개념 아님 |
| **XDR** (Extended Detection and Response) | 단말·메일·네트워크·클라우드 등 다수 보안 신호의 연관 탐지·대응 | 공급자별 데이터 통합 범위·자동대응 상이. 도입만으로 가시성 보장 안 됨 |
| **EDR** | 엔드포인트 행위 수집·탐지·조사·대응 | 악성행위 조사·격리 지원. 전통적 백신/EPP와 목적 일부 중첩 |
| **EPP** | 엔드포인트 예방·보호 | 악성코드 차단·보호 중심. EDR과 배타적이지 않음 |
| **SIEM** | 여러 로그·이벤트의 수집·상관·검색 | 정규화·보존·탐지 규칙·관제. XDR과 기능이 중첩될 수 있으나 동일어 아님 |

**연습 사고:** 원격 직원의 새로운 장치에서 비정상 로그인 후 대량 조회가 발생한다. ZTNA는 자원 접근 정책·기기 상태를 판단하고 XDR/SIEM은 신호를 상관분석한다. 조사 결과 없이 유출이라고 **확정하지 않는다**. NIST의 제로 트러스트는 네트워크 내부라는 이유만으로 신뢰를 부여하지 않는다. ([NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final))

## 4. REST API와 OWASP API Security Top 10 (실기 7쪽)

- **REST**는 자원을 URI로 식별하고 HTTP 메서드와 표현을 이용하는 아키텍처 스타일. 모든 HTTP JSON API가 REST 원칙을 완전히 지키는 것은 아니다.
- **주요 HTTP 메서드:** GET은 조회, POST는 처리/생성, PUT은 지정 자원 대체, PATCH는 부분 변경, DELETE는 제거를 일반적으로 나타낸다. 실제 서버 구현·멱등성·부작용은 설계에 따라 검증한다.
- **상태코드:** 200 성공, 201 생성, 400 잘못된 요청, 401 미인증, 403 권한 거부, 404 미존재/비공개 자원 처리에 쓰일 수 있다. 401과 403을 혼동하지 않는다.
- **기본 통제:** TLS, OAuth2/OIDC의 적절한 토큰 검증(발급자·대상·만료·서명), **자원별 서버 인가**, 과다 응답 방지, 입력 스키마 검증, 요청 횟수·동시성·비용 한도, 자원별 감사 로그. **CORS는 인증/인가 시스템이 아니다.**

### OWASP API Top 10:2023 전체 10개 범주와 방어

| 번호 | 영문 원문/학습 의미 | 위험 예시(가상) | 방어와 확인 |
|---|---|---|---|
| API1 | Broken Object Level Authorization (객체 수준 인가 실패) | 문서 ID만 바꾸면 타인의 문서 조회 | 객체 소유·공유 정책을 서버에서 검사, 다른 계정 음성 테스트 |
| API2 | Broken Authentication (인증 실패) | 약한 세션 검증/토큰 처리 | 토큰 검증·재인증·세션 만료 |
| API3 | Broken Object Property Level Authorization (속성 수준 인가 실패) | 일반 사용자가 `isAdmin` 수정/비밀 필드 응답 | 읽기/쓰기 속성 허용 목록, DTO/스키마 검증 |
| API4 | Unrestricted Resource Consumption (무제한 자원 소비) | 큰 페이지·반복 호출로 CPU/요금 급증 | 페이지 크기·쿼터·타임아웃·동시성 제한 |
| API5 | Broken Function Level Authorization (기능 수준 인가 실패) | 일반 사용자가 관리자 API 호출 | 역할/속성별 기능 권한 검사, 403 테스트 |
| API6 | Unrestricted Access to Sensitive Business Flows (민감 업무 흐름 남용) | 정상 API로 자동화 대량 주문/예약 | 업무 단위 속도·이상탐지·거래 검증 |
| API7 | Server Side Request Forgery (SSRF) | 서버가 임의 URL을 대신 요청 | 목적지·프로토콜 제한, 네트워크 egress 통제 |
| API8 | Security Misconfiguration (구성 오류) | 개발용 디버그/과도한 CORS | 안전한 기본값·설정 검사·불필요 기능 제거 |
| API9 | Improper Inventory Management (자산/버전 관리 실패) | 방치된 옛 API 버전 노출 | API·버전·소유자 인벤토리, 폐기 정책 |
| API10 | Unsafe Consumption of APIs (외부 API 불신 실패) | 외부 응답을 검증 없이 처리 | 응답 검증·타임아웃·서명·오류 처리 |

**객체 vs 기능 vs 속성 차이:** API1은 *어떤 문서*, API5는 *어떤 관리자 기능*, API3은 *문서 안의 어떤 필드*를 허용할지의 문제이다. ([OWASP 원문](https://api-security.owasp.org/editions/2023/en/0x11-t10/))

### 방어적 의사코드 실습: 권한 판정

```python
def read_document(authenticated_user, document_id, store):
    doc = store.get(document_id)
    if doc is None:
        return 404, {"error": "not found"}
    if authenticated_user is None:
        return 401, {"error": "authentication required"}
    if not (doc.owner_id == authenticated_user.id or
            authenticated_user.id in doc.reader_ids):
        return 403, {"error": "forbidden"}
    return 200, {"id": doc.id, "title": doc.title}  # 허용된 필드만 반환
```

학습용 의사코드이며 실제 서버는 미인증·존재 여부 노출에 대한 정책을 통일하고, 레코드 조회·권한검사를 원자적으로 보호하며 감사 로그·테스트를 추가해야 한다. **문서 ID가 랜덤이라는 사실은 인가 검사를 대체하지 못한다.**

## 5. 양자내성암호(PQC) · 동형암호 · 경량암호 (필기 일반 4쪽, 실기 11쪽)

| 개념 | 해결하려는 문제 | 기억할 한계 |
|---|---|---|
| **PQC** Post-Quantum Cryptography | 장래의 양자 컴퓨터에 대비한 **키 설정/서명** 등 공개키 암호 체계 | PQC = 양자컴퓨터 사용 암호(QKD)가 아니고 기존 모든 암호를 무조건 대체하는 표현도 아님 |
| **동형암호** Homomorphic Encryption | 암호문 상태에서 특정 연산 수행; 복호화 결과가 평문 연산과 연결 | 부분/일부/완전 동형암호(PHE/SHE/FHE) 유형·연산·노이즈·성능 비용이 다름; 실행환경 전체 보호와 동일하지 않음 |
| **경량암호** Lightweight Cryptography | 메모리·전력·회로 자원이 작은 IoT/임베디드 환경에서 효율적 암호 | '짧고 약한 암호' 뜻이 아님. 보안성·구현·환경 적합성을 따져야 함 |

### NIST 표준을 기능과 연결하기

- **FIPS 203 (2024)**: **ML-KEM**, 공개 채널에서 **공유 비밀을 설정**하기 위한 키 캡슐화. 메시지에 직접 전자서명하는 알고리즘이 아니다.
- **FIPS 204 (2024)**: **ML-DSA**, 격자 기반 **전자서명·검증**.
- **FIPS 205 (2024)**: **SLH-DSA**, 해시 기반 **전자서명·검증**.
- **SP 800-232 (2025)**: **Ascon-AEAD128**, **Ascon-Hash256**, **Ascon-XOF128**, **Ascon-CXOF128** 등 제약장치용 경량 암호 기능.
- NIST 문서에 정오표 또는 수정계획이 있을 수 있으므로 **정책/코드에 실제 도입할 때 최신 표준·정오표·구현 검증**을 재확인한다.

**사례:** 장기간 보관할 민감한 세션 협상에 양자 위협을 고려한다면 PQC 키 설정 전환이 논점이다. 외부 서버에 민감 통계를 위탁 계산하려면 동형암호의 지원 연산·성능을 평가한다. 배터리 제약이 큰 센서의 통신 보호라면 경량 AEAD의 환경 적합성을 검토한다. 셋은 교환 가능한 명칭이 아니다.

### 개념 실험(암호 라이브러리 없이 식으로 이해)

부분 동형의 대표적 성질을 **추상적으로** 표현하면 `Dec(Enc(a) ⊕ Enc(b)) = a + b` 같은 관계가 가능하다. 여기서 `⊕`는 해당 방식에서 정의된 **암호문 연산**으로 XOR 기호를 뜻하지 않는다. **모든 동형암호가 모든 연산을 제공하는 것이 아니고**, 이 식만으로 안전성을 입증할 수 없다.

출처: [NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) · [204](https://csrc.nist.gov/pubs/fips/204/final) · [205](https://csrc.nist.gov/pubs/fips/205/final) · [SP 800-232](https://csrc.nist.gov/pubs/sp/800/232/final).

## 6. 딥페이크·생성형 AI 보안 (필기 일반 4쪽)

- **딥페이크**: 합성·변조된 영상/음성/이미지가 실제 인물·사건처럼 보이도록 하는 기술 및 결과물. 피싱, 허위 지시, 사칭, 증거 조작 문제와 연결된다.
- **위험 시나리오**: 임원 음성 사칭으로 송금 지시 → 직원이 평소 절차를 생략 → 부정 송금. 예방은 '음성 탐지기 100% 믿기'가 아니라 **독립 채널 재확인, 이중 승인, 고위험 지시의 업무절차 검증**, 원본·촬영경위·서명 등 출처 확인의 조합.
- **생성형 AI 시스템 추가 위험**: 프롬프트 인젝션, 민감정보 입력·학습 데이터 노출 가능성, 출력 내용의 사실성·저작권·편향, 모델·데이터 공급망. 딥페이크와 모든 AI 보안을 동일어로 사용하지 않는다.
- **검증 한계**: 'AI 탐지 점수', 워터마크 부재, 사진 메타데이터만으로 진위 여부를 결정하지 않는다. 분석 결과에는 확률과 불확실성을 명시한다.

## 7. 2027 실기에 연결되는 기존 필수기술 확장

### OS·서비스 보안 점검
- 계정/권한/패치/원격 관리/파일 공유/로그·보존정책을 **설정값과 증거**로 설명하고 비인가 서비스·열린 포트를 분리 기록한다.
- FTP/SFTP/메일 SMTP·POP3·IMAP/웹·WAS/DNS/DB의 구성·전송 보호·권한·감사 설정을 서비스별로 분리한다. **SFTP는 SSH 기반 파일 전송으로 FTPS(FTP+TLS)와 다르다.**
- WAF, IDS/IPS, Anti-DDoS, Anti-APT의 정책 효과와 오탐·정상 서비스 영향을 함께 평가한다.

### 네트워크·장비
- **PDU 분석**: Ethernet 프레임→IP 헤더→TCP/UDP 헤더→응용 데이터를 단계별로 해석; 단, TLS 암호화 페이로드의 내용을 패킷 헤더만으로 알 수 없다.
- **SNMP**: 네트워크 장비 모니터링/관리 프로토콜. 설정·접근 권한·버전별 보호 범위를 고려하며 권한 없는 폴링을 하지 않는다.
- **VLAN**: 논리적 L2 분리. VLAN 자체가 사용자 인증·완벽한 보안 경계를 제공한다고 단정하지 않고 라우팅/ACL·트렁크 정책을 함께 본다.
- **EDR vs EPP**: EPP는 보호/예방 중심, EDR은 행위 텔레메트리·조사/대응 중심. 제품마다 범위가 겹친다.

### 점검 이력·로그·위험
- 점검 표준 항목: `자산-ID / 일시·시간대 / 점검 범위·도구 / 발견 근거 / 영향 / 우선순위 / 담당자 / 조치기한 / 증빙 / 재검증 / 잔여위험`.
- 로그 상관분석은 **시간대(UTC/KST)·시각 오차·원본 보전·요청 ID·IP/NAT 공유**를 고려한다. 로그인 1건과 자료 전송 1건을 같은 인물의 확정 행위로 단정하지 않는다.
- 위험 `가능성 × 영향`은 **예시 척도**일 수 있으며 공식 점수표가 유일하다고 보지 않는다. 위험 회피·감소·전가·수용의 이유를 자산 중요도, 비용, 기한, 책임자와 연결한다.

## 8. 자체 확인 문제 (비공식)

1. 컨테이너 이미지 스캔이 성공했는데도 운영 서비스 위험이 남는 이유 세 가지는?
2. Trivy와 ScoutSuite의 주요 입력 대상과 결과 유형은?
3. SASE와 ZTNA는 포함관계인지 동일어인지? 주의점은?
4. XDR과 EDR, SIEM의 차이를 수집 범위·분석·조치 관점으로 구별하라.
5. API1/API3/API5는 각각 어떤 허용 결정을 실패한 것인가?
6. SG가 상태 저장이라고 NACL과 라우팅 설정을 무시할 수 있는가?
7. ML-KEM과 ML-DSA를 바꿔 쓰면 안 되는 이유는?
8. '동형암호는 암호문을 사용하므로 모든 계산이 무료'라는 주장의 문제는?
9. 제한된 센서에서 경량암호를 선택할 때도 고려할 세 가지는?
10. 임원 음성이 진짜로 들려도 송금 승인 전 필요한 통제는?

### 자체 해설(공식 정답 아님)

1. 런타임 설정·계정/권한·네트워크/앱 인가 오류 등은 이미지 스캔 밖에 남을 수 있다.
2. Trivy는 이미지·파일·IaC 등에서 알려진 취약점·구성 문제를, ScoutSuite는 클라우드 계정 설정의 위험 신호를 본다.
3. ZTNA는 자원 접근 정책/구현으로 SASE의 보안 기능에 포함될 수 있으나 두 용어는 같지 않다.
4. EDR=단말 중심, XDR=다중 보안 신호 상관 탐지/대응, SIEM=광범위 로그 관리·분석. 제품별 중첩 주의.
5. API1=객체, API3=필드/속성, API5=기능 수준의 서버측 인가.
6. 불가. 네트워크 경로와 다른 정책 계층을 별도로 평가한다.
7. KEM=공유 비밀 설정, DSA=전자서명/검증. 기능 목적이 다르다.
8. 종류별 지원 연산과 암호문 크기·계산·통신 비용이 다르다.
9. 구현 보안, 성능·전력/메모리, 키·nonce 관리 및 검증된 표준.
10. 별도 연락 경로 확인, 사전 지정된 다중 승인, 거래 조건·계좌 재확인.

연습 사례와 문제는 **전부 자체 제작**이며 출제기관 기출·복원문제에 해당하지 않는다. [실기 사례형 워크북](./2027_PRACTICAL_WORKBOOK.md)에서 풀이 방법을 연습한다.
