# 2027–2029 정보보안기사 실기 연습 워크북

> **전 문제·사례·로그·IP·금액은 학습 목적으로 직접 만든 가상 예시입니다. 공식 기출문제, 복원문제, 공식 모범답안이 아닙니다.**  
> 대상: 공식 실기 출제기준의 ① 보안 특성 파악 ② 취약점 점검·보완 ③ 로그 수집·분석 및 침해 대응 ④ 위험분석·대책 수립 ⑤ 최신 보안 동향. **실제 환경의 접근 권한·계정·토큰·고객정보를 공개 GitHub 문서에 기록하지 않는다.**

## 작성형 답안의 원칙

1. **대상/정상 동작**을 먼저 정의한다.
2. **취약점·위협·원인**을 혼동하지 않고 관찰 결과와 가설을 나눈다.
3. **영향 범위·우선순위**를 평가한다.
4. **최소권한·설정·모니터링 등 통제**를 설명한다.
5. **설정 증거·재검증·담당자/기한**까지 적는다.

연습 시간 예시: 20분에 단답 5개 + 40분에 사례형 2개. 이것은 공식 시험의 실제 배점·문항 구성을 나타내지 않는다.

## A. 시스템·네트워크 보안 특성 파악

### A1. 주소·서브넷 계산

**문제(자체 제작)**: 가상 웹 구간 `10.20.30.0/27`에 대해 전체 주소 수, 일반적인 할당 가능 호스트 수, 네트워크 주소, 브로드캐스트 주소, 일반적 할당 주소 범위를 구하라. 또 `/31`의 특수 용도를 한 줄로 설명하라.

**해설**: `2^(32-27)=32`개, 전통적인 IPv4 서브넷에서 30개 호스트, 네트워크 `10.20.30.0`, 브로드캐스트 `10.20.30.31`, 통상 `10.20.30.1–10.20.30.30`. `/31`은 RFC 3021의 **점대점 링크**에서 두 주소를 사용할 수 있으므로 '항상 0개 호스트'라고 일반화하면 안 된다.

### A2. 가상 VPC/SG 규칙 검토

다음은 실제 계정이 아닌 **가상 보안그룹 설계표**다.

| 자원 | 인바운드 규칙 | 의도 |
|---|---|---|
| WEB-SG | TCP/443 from `0.0.0.0/0` | 외부 HTTPS |
| WEB-SG | TCP/22 from `0.0.0.0/0` | 관리자 SSH |
| APP-SG | TCP/8080 from WEB-SG | 웹→앱 |
| DB-SG | TCP/5432 from `0.0.0.0/0` | 앱→DB |

**문제(자체 제작)**: 과도하게 열린 규칙 두 개를 찾고 개선안을 쓰라. SG가 **상태 저장**임이 반환 트래픽에 미치는 영향도 설명하라.

**해설**: 웹 SSH/22 전체 공개는 관리자 사설/VPN·접근 관리 경로로 제한, DB/5432 전체 공개는 APP-SG 또는 필요한 서버로 제한한다. SG의 상태 추적에 따라 **허용된 연결의 응답**은 통상 역방향 별도 허용 규칙 없이 통과할 수 있다. 그러나 라우트/공인 주소/NACL/호스트 방화벽·인증까지 고려해야 한다. **443 전체 공개는 공개 웹 서비스라는 요구에 따라 정상일 수도 있다.** ([AWS VPC](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html))

### A3. 엔드포인트 보안 비교

**문제(자체 제작)**: EPP가 설치된 단말에서 의심스러운 PowerShell 실행이 탐지되었다. EPP와 EDR의 역할, 대응 시 증거 보존을 각각 설명하라.

**해설**: EPP는 악성코드 예방·차단을, EDR은 실행 프로세스/명령행/연관 이벤트 조사·격리·대응을 중심으로 설명한다. 탐지 이유와 실행 시각, 프로세스 계보, 사용자·호스트, 차단 결과를 보존한다. **탐지 알림만으로 감염 확정 금지.** 제품별 기능은 다를 수 있다.

### A4. 네트워크 장비와 프로토콜

**문제(자체 제작)**: VLAN을 나누면 다른 VLAN 사이에 절대로 통신이 불가능한가? SNMP 장비관리와 라우터 ACL을 같이 점검하는 이유는?

**해설**: VLAN은 L2 논리 구분이므로 라우팅·방화벽 정책에 따라 VLAN 간 통신이 가능할 수 있다. SNMP는 장비 모니터링/관리 접근을 제한하고 필요 시 보호 기능을 점검한다. 라우터 ACL은 인터페이스/방향별 허용 통신을 통제한다. 장비 구성, 실제 경로, 관리망 접근 정책을 검증한다.

## B. 취약점 점검과 조치이력

### B1. Dockerfile 구성 점검 (본인 PC에서만)

```dockerfile
# 연습용 취약 구성 예시: 실제 서비스에 배포 금지
FROM alpine:3.20
USER root
CMD ["sh", "-c", "echo training only"]
```

**문제(자체 제작)**: 최소 세 가지 확인 사항을 제시하고, Trivy로 할 수 있는 점검과 할 수 없는 점검을 구분하라.

**해설**: root 사용자 필요성, 베이스 이미지 갱신 및 버전 고정 정책, 불필요 패키지·비밀 포함 여부, 읽기전용 파일시스템/권한, 공급망 출처 확인. `trivy config <Dockerfile-포함-폴더>`는 IaC 구성 점검, `trivy image <본인-이미지>`는 이미지의 알려진 취약점 등 점검에 사용한다. 서비스 소유자 권한(예: 문서 열람) 같은 **비즈니스 인가 실패**는 이 점검만으로 보장되지 않는다. ([Trivy](https://trivy.dev/docs/latest/scanner/misconfiguration/))

### B2. 점검 이력 기록 실습

다음 샘플의 `상태`를 포함하여 **재점검 절차**를 작성하라.

| 발견 ID | 가상 자산 | 발견 | 증거(가상) | 영향 | 담당자 | 기한 | 상태 |
|---|---|---|---|---|---|---|---|
| F-01 | WEB-01 | 불필요 SSH 공개 | 인바운드 `0.0.0.0/0:22` | 높음 | 운영담당 | D+2 | 진행 중 |
| F-02 | DB-01 | 계정 최소권한 미흡 | 읽기 계정에 쓰기 권한 | 높음 | DB담당 | D+4 | 미조치 |
| F-03 | API-01 | 감사 로그 없음 | 읽기 요청 ID 미기록 | 중간 | 개발담당 | D+7 | 조치완료(미검증) |

**해설:** F-01: SG 설정 변경 이력 및 의도한 관리자 출발지에서만 연결되는지 재검증, F-02: 역할별 권한 확인·업무 테스트, F-03: 실제 생성 로그의 시간/요청 ID/접근권한/보존·개인정보 최소화를 재확인. **'조치완료'와 '재검증 통과'를 분리**하고 기한 초과·반복 항목을 추적한다. 증빙에는 계정번호·토큰·IP 등 민감정보를 비식별화한다.

### B3. 서비스 보안 점검표

**문제(자체 제작)**: 파일서버, 메일서버, WEB/WAS, DNS, DB 각 1개씩 핵심 설정 점검 포인트를 적으라.

**예시 해설**:
- 파일/공유: 익명 접속·과도한 ACL·불필요 공유 여부.
- 메일: 오픈 릴레이, SMTP 인증/전송 TLS, POP3/IMAP 보안 연결 여부.
- WEB/WAS: 디버그 모드, 관리자 노출, TLS/보안 헤더 및 권한.
- DNS: 불필요한 재귀·영역 전송·관리 권한 여부(서버 역할에 맞춰 점검).
- DB: 객체(테이블·컬럼·뷰)별 권한, 저장 암호화·백업·감사.
- 각 항목은 **발견→원인→변경 전 백업→조치→기능 테스트→재점검**을 한 행으로 남긴다.

## C. REST API 인가·로그 및 침해 대응

### C1. 가상 REST API 권한

**가정**: 사용자 `u1`은 자신이 소유한 `/api/reports/r1`만 읽을 수 있고 관리자 기능은 사용할 수 없다.

| 요청(가상) | 기대 응답 | 이유 |
|---|---|---|
| `u1: GET /api/reports/r1` | 200 | 소유자 조회(정상 인증과 인가를 전제) |
| `u1: GET /api/reports/r2` | 403 또는 정보 노출 방지를 위한 404 | 타인 객체(서버 정책을 통일할 것) |
| `u1: POST /api/admin/users` | 403 | 일반 사용자에게 관리자 기능 없음 |
| `u1: PATCH /api/reports/r1 {"isAdmin":true}` | 속성 변경 거부 | 해당 속성은 사용자 편집 권한 밖 |

**문제(자체 제작)**: 각 실패를 OWASP API1·API3·API5 중 가장 관련 높은 항목으로 연결하라. 인증이 없다면 어떤 상태코드를 고려할까?

**해설**: 타인 보고서=API1, `isAdmin` 필드=API3, 관리자 기능=API5. 미인증 요청은 일반적으로 401로 처리. 성공 상태코드는 **설계한 계약·리소스 상태에 따라** 달라질 수 있다. 서버가 실제로 권한을 집행하는지 **소유한 테스트 계정 2개**로 검증해야 한다. ([OWASP API 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/))

### C2. 타임스탬프가 다른 가상 로그인 로그

다음은 전부 **조작된 연습용 로그**로 실제 침해·개인정보 기록이 아니다.

```text
2027-02-01T12:00:00Z   auth    login_failed user=demo src=198.51.100.18
2027-02-01T21:00:06+09:00 auth login_success user=demo src=198.51.100.18
2027-02-01T12:00:09Z   api     GET /api/reports/r1 user=demo status=200 bytes=812
2027-02-01T12:00:11Z   api     GET /api/reports/r2 user=demo status=403 bytes=58
2027-02-01T12:02:30Z   fw      connection_allowed src=198.51.100.18 dst=203.0.113.10:443
```

IP 주소는 문서·교육용 예약 블록(198.51.100.0/24, 203.0.113.0/24)을 사용한다.

**문제(자체 제작)**: 로그를 UTC 기준으로 정렬하고, **확정 가능한 사실 3개**, **확정할 수 없는 판단 2개**, 추가로 확인할 로그 3종류를 제시하라.

**해설:** 두 번째 줄 21:00:06+09:00은 **12:00:06Z**이다. 순서는 12:00:00 실패→12:00:06 성공→12:00:09 r1 성공→12:00:11 r2 거부→12:02:30 방화벽 허용. 확인된 것은 동일 사용자 문자열의 인증 실패·성공, 객체 조회의 HTTP 코드, 네트워크 허용 이벤트이다. **실제 데이터 유출·계정 탈취의 확정, 단일 사람이 모두 수행했다는 결론**은 성립하지 않는다. 확인할 것은 인증 장치·MFA/세션 발급 로그, API 요청 ID/객체 인가/전송 로그, 프록시·NAT/엔드포인트 로그다. 시각 동기화·로그 완전성·데이터 보존을 점검한다.

### C3. 의심 사고의 초기 대응

**문제(자체 제작)**: 위 C2에서 r2에 대한 403이 5,000건 발생했다고 가정한다. 실행 가능한 우선 대응 4단계를 적되 오탐도 고려하라.

**해설:** (1) 탐지 경보의 규칙·기간·샘플을 확인, (2) 영향 서비스/계정 식별 및 승인된 임시 접근제한·속도제한, (3) 원본 로그·시각·연관 ID를 보존하면서 과도한 호출 원인을 조사, (4) 비밀번호/세션·권한 정책을 점검하고 조치 후 정상 기능과 재발 탐지를 검증. **403은 차단의 증거이지 200 응답 또는 유출의 증거가 아니다.**

## D. 위험분석과 정보보호 대책 수립

### D1. 위험도 매트릭스 (학습용, 공식 채점식 아님)

가상의 평가정책 `위험도 = 발생가능성(1~5) × 영향도(1~5)`, `12 이상 우선 처리`를 사용한다.

| 시나리오 | 가능성 | 영향 | 계산 |
|---|---:|---:|---:|
| WEB-01 SSH 전체 노출 | 4 | 4 | 16 |
| API-01 감사 추적 미흡 | 3 | 4 | 12 |
| DB-01 권한 과다 | 2 | 5 | 10 |

**문제(자체 제작)**: 우선 처리할 항목과 이유, **DB-01도 조치해야 할 수 있는 이유**, 허용 가능한 잔여위험 결정의 책임을 기술하라.

**해설:** 예시 정책상 WEB-01, API-01이 12 이상이다. 그러나 DB-01의 높은 영향과 법적·규제 조건에 따라 점수 10이라도 즉시 통제가 필요할 수 있다. 위험 수용은 **정해진 권한을 가진 책임자**가 근거·기간·재평가 조건을 남겨 결정해야 한다. 점수 모델을 공식 시험의 유일한 방식으로 주장하지 않는다.

### D2. 연간 기대손실 계산

**문제(자체 제작)**: 가상 자산가치 8,000만 원, 노출계수 25%, 연간 발생빈도 0.2회. SLE와 ALE를 계산하고 한계 1개를 쓰라.

**해설:** SLE=8,000만 × 0.25 = **2,000만 원**. ALE=2,000만 × 0.2 = **연 400만 원**. 실제 손실의 확정 금액이 아니라 가정한 빈도·노출계수에 따라 달라지는 기대값이다.

### D3. 대응계획/잔여위험

**문제(자체 제작)**: F-01(SSH 공개)의 **위험 감소**, F-02(DB 권한 과다)의 **위험 회피·감소**, 외부 계약을 통한 **위험 전가**, **위험 수용**의 차이를 설명하고 이행계획 표를 완성하라.

| 항목 | 예시 조치 | 책임/기한 | 검증 | 잔여위험 |
|---|---|---|---|---|
| F-01 | VPN/관리망에서만 SSH 허용 | 운영담당 / D+2 | SG 규칙+접속시험 | 관리키 탈취 위험 별도 관리 |
| F-02 | 역할별 최소권한·쓰기 금지 | DB담당 / D+4 | 읽기/쓰기 권한 음성 테스트 | 승인된 계정 오남용 |
| 개인정보 과다 보유 | 목적·기한·파기 정책 점검 | 개인정보담당 / D+7 | 보유 표·파기 증빙 | 예외·백업 잔존 여부 확인 |

**해설:** 회피=위험을 만드는 활동 자체를 중단, 감소=노출·가능성·영향을 줄임, 전가=보험/계약 등으로 손실 부담 일부를 이전(법적 책임 전체를 없애지는 못함), 수용=승인 조건으로 잔여위험 감수. 조치 우선순위는 점수뿐 아니라 법 준수·자산 중요도·예산·완료기한·업무영향도 본다.

## E. 최신 보안 동향 및 필기 추가 확인

### E1. 암호 기능 구별

**문제(자체 제작)**: 다음 선택지 중 적절한 용도를 각각 고르라. (1) 미래 양자 위협을 고려한 세션 비밀 설정 (2) 장치의 서명 검증 (3) 암호문에 대한 특정 집계 연산 (4) 제한된 센서의 인증 암호화.

**해설:** (1) ML-KEM 같은 PQC KEM, (2) ML-DSA/SLH-DSA 같은 PQC 서명, (3) 지원 연산과 성능을 확인한 동형암호, (4) 표준화된 Ascon-AEAD128 같은 경량 AEAD 검토. **PQC는 동형암호·경량암호의 동의어가 아니다.** ([FIPS 203](https://csrc.nist.gov/pubs/fips/203/final), [204](https://csrc.nist.gov/pubs/fips/204/final), [205](https://csrc.nist.gov/pubs/fips/205/final), [SP 800-232](https://csrc.nist.gov/pubs/sp/800/232/final))

### E2. 딥페이크 AI 검증(필기 연계)

**문제(자체 제작)**: 화상회의에서 특정 임원이 '새 계좌로 긴급 송금'을 지시한다. AI 탐지기가 '정상'이라고 표시해도 승인 전 필요한 절차를 쓰라.

**해설:** 평소 사용하던 **독립적인 연락 수단으로 당사자 확인**, 사전 승인된 다중 결재·계좌 등록/변경 검증, 통화 원본·회의 기록 관리 등. 탐지기 결과만으로 진위를 확정하면 안 된다. 딥페이크 AI는 **필기 정보보안 일반**에 명시되며 실기 최신동향 세세항목(양자내성·동형·경량)과 구분한다.

## F. 자기채점 체크리스트

- [ ] 용어 정의가 정확하며 보안 목적을 설명했다.
- [ ] 정상 동작과 위험 시나리오를 분리했다.
- [ ] 취약점의 **근거**와 미확인 추정을 구분했다.
- [ ] 기술적 통제와 조직적 승인·업무영향을 함께 적었다.
- [ ] **실제 설정 변경 없이도** 안전하게 검증할 자료·방법을 제시했다.
- [ ] 조치일·담당자·재검증·잔여위험을 기록했다.
- [ ] 공식 기출/공식 출제빈도·법규 최신 상태라고 잘못 표기하지 않았다.

## G. 실습 환경·출처와 업데이트 책임

- 실습은 **자신의 가상 계정·localhost·가상 로그**에서 수행. 외부 계정에 대한 Nmap·클라우드 스캔·API 테스트는 소유자 사전 승인 없이는 수행하지 않는다.
- 공개 저장소에는 **API 키/클라우드 계정 식별정보/개인정보/실제 사고로그/ScoutSuite 원본 리포트**를 업로드하지 않는다.
- 도구의 CLI 플래그·결과는 버전별로 다를 수 있다. 실제 실행 전 도구 버전·공식 문서와 권한을 확인한다.
- `security-concept-handbook.pdf` / `security-review-pack.pdf`는 각각 2023–2026 기준 중심의 **선행·복습 자료**로 사용하며 이 문서가 원본 PDF를 개정·교체한 것은 아니다.
- 법령명/의무/신고기한/인증제도는 시험 시점 기준으로 [국가법령정보센터](https://www.law.go.kr)와 [KCA 출제기준](https://www.cq.or.kr/qh_cusgm10_001.do)을 다시 검증한다.
